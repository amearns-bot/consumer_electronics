05 · New: raw data head start

Brand tracker rebuilt on a real Qualtrics export shape

Cross-checked against two real files attached to the project (the "Dyson Prototype" BX BrandAwareness survey's raw XML export and its question-text codebook CSV) — full detail in dyson_demo_data/brand_tracker_codebook.md.

What changed

The brand tracker is no longer an invented single-brand score. It's a genuine competitive tracker across Dyson, Shark, Philips, Samsung, Sony, with per-brand ad exposure, consideration-set membership, and self-reported ownership — matching what the real attached survey actually asks.

Raw → derived pipeline

brand_tracker_RAW_qualtrics_export.csv is shaped exactly like a real Qualtrics export (3 header rows: tag / question text / ImportId). The readable brand_tracker_survey.csv is now computed from it — a small, concrete proof of the raw→identity→derived pipeline in Section 08 below, not two independently invented files.

Codebook caveat

Column tags, question text, and the QID mapping are verified — copied straight from the attached files. Value-level codes (brand order, ad-channel codes, attribute codes, demographic brackets) are inferred placeholders, built to be internally consistent but not confirmed against Dyson's real codebook yet — see the codebook doc for exactly which is which.

Bonus finding: cross-checking against the real survey showed a general-population brand tracker has no way to know about post-purchase assembly-latch friction — so Physical_Onboarding was removed from the brand tracker file and now lives only in owner_onboarding_survey.csv, which is architecturally the correct place for it. A direct improvement from grounding in real data instead of inventing the schema top-down.

07 · New: end-to-end connected journey

Tying BX + DX + CX together against what Dyson actually called out

Full detail in dyson_bxdxcx_connected_journey_and_build_plan.md. Every claim below traces back to a specific citation in the RFP submission framework or the platform demo playbook — not invented.

Dyson called outWhat it's really asking
"One identity, three signals"A single identity that brand, digital, and service data all resolve to
"How do customers move between channels (DX↔CX)?"A website friction event and the resulting support call are currently invisible to each other
Contact center is "a critical blind spot"Call content isn't analyzed beyond post-call CSAT
9-year Kantar baseline continuityThe migration off Kantar can't break longitudinal comparability — a transition requirement, not a reason to keep Kantar running
"Always-on, not waves only"Periodic rigor and continuous signal, simultaneously
Strategic outcome, stated plainly: full Kantar displacement, not coexistence. Qualtrics' native Brand Experience capability replaces Kantar entirely — the parallel-run/statistical trend-matching period is the de-risking transition mechanism, the same posture already used to displace Medallia in DX with no hedging. That parallel run runs on its own research-methodology timeline (multiple tracking waves, not weeks) — separate from the demo/data build timeline in Section 07.

Scenario 1 — Premium Promise vs. Reality

Resolves "one identity" + DX↔CX movement. XID resolves Sarah's anonymous web session (Adobe ECID) to her CRM record (MCID) before she contacts support — recovery is proactive, not reactive.

Scenario 2 — Self-Service Worthy of the Brand

Resolves the contact-center blind spot. Proves a support call was "failure demand" caused by a broken app video, routes evidence straight to engineering — collapsing signal-to-remediation time per Dyson's own definition of "connected."

Scenario 3 — Brand Health with the "Why"

Resolves Kantar displacement + always-on/waves tension. Brand tracking runs natively on Qualtrics post-cutover — the formal wave still locks periodically for board reporting, but the continuous read underneath it is native rather than bridged through a third-party panel vendor.

08 · New: XID architecture & build effort

How multiple datasets actually tie together — and what it costs to build

The current dataset uses one flat key (OO-00001) as a shortcut. The real/target architecture needs three identity tiers, because Dyson's own data doesn't arrive pre-resolved either.

TierIdentity typeResolves to individual?
1 — DeterministicXID, backed by Dyson's MCIDYes — ground truth once registered/ordered
2 — ProbabilisticAdobe ECID (anonymous web session)Only after a later deterministic event stitches it to MCID
3 — Aggregate/proxyChannel + cohort tags only (social listening, non-registered retail)No — must not be forced to individual XID
Effort flagged

Building this properly means rebuilding the dataset files so their keys actually follow the 3-tier model above — not the current flat-key shortcut. That's estimated as a Medium–Large phase, not yet started, on top of the Small/Medium phases already complete (schema design, per-source dataset build). See the full phase table and sizing in dyson_bxdxcx_connected_journey_and_build_plan.md — includes what's specifically needed from Dyson (real MCID format, GCP MADE schema sample) before the identity-resolution story is more than illustrative, and a risk flag that this phase is the one most likely to get compressed before Sep 24.
